## Question

预热协调、事件驱动和共享盘口合并后，双腿超限与空等减少多少，机会有效性是否仍满足现有约束？

## What to build

通过正式扫描服务和原生 worker 做同口径的离线前后对照，以方向一落地、方向二改动前的版本为基线。记录两版源码身份、worker 构建和夹具、请求限频配置、轮次与统计口径。

## 验收条件

- [x] 在 16、64、256 盘口下逐档报告双腿时差 P95/P99、超过 1 秒的比例、重试量、路线等待时间、首轮耗时和新鲜覆盖率。列明样本数、覆盖率分母及未完成轮次。覆盖率按固定间隔观测，独立于扫描唤醒频率。
- [x] 结合现有离线注入能力，记录不同步预热、慢来源、429 和共享盘口下的请求与路线推进。区分等待预热或退避与已就绪后的调度等待，并核对可服务路线的等待时间是否在 03 确定的上界内。
- [x] 通过正式机会发布和批准入口核对 5 秒盘口时效、1 秒双腿时差、行情不健康后撤回机会和批准时复核有效期，并保留可复核的离线运行证据。

## 离线复测口径

基线为 `7e30b2b68a3dd9183cf8c6971539a9d2bc1b40b8`，已包含方向一的元数据复用。对照版为合并 01–03 后的 `0fe46f9b98af6f10530b22ea14ba22a94b8472d7`。两个源码版本分别从干净检出运行。两版的原生源码和构建入口相同，均使用方向一留存的 Windows ReleaseFast worker。编译器为 Zig `0.17.0-dev.315+5b647b792`，worker SHA-256 为 `65c9f5ea46366217cd72b41abfcb2ebf0bf695b28a689246cc87bd89e4304161`。构建命令见[方向一基线](../../scanner-metadata-reuse/issues/01-warmup-baseline.md)。

两版使用同一份[容量验收脚本](../../../python/verify_scanner_capacity.py)和合成 OKX production 现货、Hyperliquid production 标准永续响应，每条 TOKEN 路线各一腿。使用正式自动扫描循环、生产限频配置和原生 RawIngress 捕获。两版均使用 OKX 100 ms、Hyperliquid 盘口和批量报价 120 ms、Hyperliquid 元数据 1200 ms 的请求间隔，活动盘口 worker 上限 16，每 Venue 行情任务并发上限 2，目录每 30 秒刷新。对照版的目录请求与行情任务共用该并发额度。

从仓库根目录执行以下命令。将同一份容量脚本复制到两个检出的 `python/` 目录，各执行一次。

```powershell
python <checkout>/python/verify_scanner_capacity.py --automatic --selected 16 64 256 --seconds 420 --rounds 1 --worker <worker.exe>
```

- 每档以一轮为目标，最多观测 420 秒。首轮由运行时记录完成时刻。新鲜覆盖从启扫起按独立的 500 ms 时刻采样，以发现路线数为分母，记录各次覆盖的均值和峰值、跳过的时刻数及最大采样延迟。请求计数截止于观测到首轮完成或超时。
- 双腿时差在正式发布步骤统计。两腿规范盘口时间都晚于该路线上一条统计样本时计为一组，纳入超限样本。P95/P99 使用最近秩。重试量记录运行时实际标记的双腿时差修复派发。
- 路线等待从启扫计至两腿各自第一次实际盘口请求中较晚的时刻，每条路线取一个样本。两版由同一夹具在 HTTP opener 记录请求时刻，这一口径涵盖预热、限频和轮转。故障夹具另用原生预热完成和实际公共请求时刻拆分等待。

## 故障注入与共享盘口

对照版在正式自动循环中运行 03 的九路线高低边际夹具。TOKEN0 的 OKX 元数据响应延迟 3.6 秒，TOKEN1 的首个 Hyperliquid 盘口响应延迟 1.6 秒，低边际 TOKEN8 的首个 Hyperliquid 盘口请求返回带 `Retry-After: 2` 的 429。时间均为启扫后毫秒。

| 路线 | 等待预热或退避 | 已就绪后的等待与推进 |
| --- | --- | --- |
| TOKEN0 | 1250 开始预热，Hyperliquid 在 1593 就绪，OKX 在 5062 就绪 | 359 ms 后两腿同时发出盘口请求，规范盘口时差 0 ms |
| TOKEN1 | 两腿在 3015 完成预热 | OKX 和 Hyperliquid 分别等候 188 ms 和 203 ms 后发出请求，首对规范盘口时差 1610 ms。慢响应期间，TOKEN3、TOKEN7、TOKEN5 和 TOKEN6 先后完成双腿采样。TOKEN1 随后在 9843 完成双腿采样，时差 0 ms |
| TOKEN8 首次 | 两腿在 5968 前完成预热 | 328 ms 后两腿发出请求，Hyperliquid 于 6296 返回 429 |
| TOKEN8 恢复 | Hyperliquid 在 8312 恢复公共报价请求，退避期间 OKX 仍请求批量报价。TOKEN8 的 Hyperliquid 于 9718 开始重新预热，10015 就绪，随后轮转的 OKX 腿于 13078 开始预热，13578 就绪 | 265 ms 后发出首个盘口请求，297 ms 后两腿均获请求，14000 前完成双腿采样，时差 32 ms。14468 发布时已计入首轮 |

TOKEN8 首次和恢复后的两腿请求等待分别为 328 ms 和 297 ms，均在 [03 的 14 秒夹具上界](03-reuse-shared-books-and-rotate-fairly.md#离线验收)内。从 Hyperliquid 恢复公共请求到 TOKEN8 开始重新预热的 1406 ms 计入恢复前等候。限频定向回归也验证了退避期间 OKX 的独立请求仍可推进。

共享场景使用同一 Instrument 的两个 OKX 环境绑定，两者指向同一个 production 公共来源。两条路线在 2719 ms 首次同时新鲜，之前实际发出 3 次 OKX 盘口请求和 4 次 Hyperliquid 盘口请求。两个 OKX 别名沿用 `759501765000000 ns` 的采样时刻和同一个 RawIngress 引用。原生重放的捕获 session 为 `2867336861288742`，原始序号为 `6`，原文 SHA-256 为 `cf33a011cccce31c3a77c0b26038ff590881f5a46046453ac201d867690aa15b`，候选复算一致。暂停派发并等在途任务结束后再等待 5062 ms，两条路线均显示过期，覆盖截止时刻和完成轮数保持不变。

原始请求、采样及覆盖记录见[预热、慢响应与 429 JSONL](../../build/scanner-paired-04-fair-rerun.jsonl)、[共享与过期 JSONL](../../build/scanner-paired-04-shared-rerun.jsonl)和[注入记录脚本](../../build/scanner-paired-04-trace.py)。

## 机会发布与批准

沿用[定向集成用例](../../../python/test_scanner_integration.py)的认证 HTTP 和原生盘口夹具。在每个批准用例里先发布一条已评估、已推荐的机会，再将同一个候选、评估摘要和有效期提交给 `POST /api/scanner` 的 `approve` 操作。核对 HTTP 400、拒绝原因和后续 `GET /api/scanner` 的机会及覆盖状态。

| 注入 | 发布与批准观测 |
| --- | --- |
| 评估期限给 6 秒，推进盘口时钟 5.001 秒 | 发布的有效期距数据截止恰好 5 秒。让批准成为推进时钟后的第一个 API 请求，返回 `expired`，后续读取得到 1 条过期路线 |
| 单腿延迟，规范盘口实际时差超过 1 秒 | 两腿仍连续，机会退出已评估和推荐状态，批准返回 `data_skew` |
| Hyperliquid 盘口请求失败 | 机会退出已评估和推荐状态，批准返回 `data_gap` |

以上三项及 Venue 限频、429 恢复、慢来源下的广域轮转共 6 项定向测试通过。运行清单及输出见[复测命令](../../build/scanner-paired-04-faults.ps1)和[定向测试日志](../../build/scanner-paired-04-eligibility.log)。
