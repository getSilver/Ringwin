## Question

怎样让已就绪的路线在上一批请求完成或限频窗口开放后及时采样？

## What to build

扫描服务由请求完成和下一次可请求时间驱动，合并短时间内的重复唤醒。仍需按时处理盘口过期、目录刷新与停扫。

## 验收条件

- [x] 经正式扫描循环记录请求完成、额度开放及后续调度的时刻。已有可服务路线时可在下一次固定 500 ms 推进前使用额度。没有可做的工作时可以等待，不忙轮询。
- [x] 用现有慢响应和 429 注入能力观察公共请求。每 Venue 并发上限、限频间隔和 `Retry-After` 生效，未受影响来源继续推进。
- [x] 无请求完成事件时仍能按期撤回过期机会和刷新目录。停扫后能正常结束调度。

## Answer

自动循环合并预热、盘口、批量报价和目录任务的完成通知。仅在路线具备派发条件时计算额度唤醒时间，并保留 500 ms 维护间隔检查盘口时效和目录刷新。目录请求与行情任务共用 Venue 并发额度。原生 worker 快速失败时，同一路线的失败 worker 按维护间隔重试。

### 离线验收

Windows 复用现有原生 `ringwin-scanner-market.exe` 和容量验收的公共协议夹具，由正式自动扫描循环驱动。以下时刻为各次启扫后的毫秒数。

| 观察 | 完成或计划时刻 | 实际时刻 |
| --- | ---: | ---: |
| OKX 独立盘口额度开放 | 请求完成 157，额度开放 163 | 调度并发出请求 188 |
| 双腿盘口额度开放 | 请求完成 2469，额度开放 2475 | 调度并发出双腿请求 2532 |
| Hyperliquid 收到 429 | 3250，`Retry-After: 2` | 5438 恢复盘口请求 |
| 慢盘口挂起期间撤回过期机会 | 最后一个请求任务完成 3297 | 8172 观察到撤回 |
| 无完成事件时触发目录刷新 | 8172 将目录设为到期 | 8703 观察到目录预留额度，8844 在有空位后发出请求 |
| 停扫和关闭 | 8938 进入 `Stopped` | 9125 确认自动循环线程已退出 |

慢响应期间，两家 Venue 的实际公共请求并发峰值均为 2。429 运行中，同一 Venue 的最短相邻请求间隔为 OKX 109 ms、Hyperliquid 156 ms，Hyperliquid 退避期间 OKX 独立盘口继续发出 12 次请求。维护运行在 3297 至 8781 ms 之间没有请求任务完成，仍撤回过期机会并触发目录刷新。刷新到期时 OKX 两个额度均占用，先等待空位再请求。

7 项现有定向回归通过，覆盖公共限频、慢来源、429 恢复、盘口过期、目录 TTL、旧目录结果隔离和 worker 轮转。工作区离线原始记录见 `.scratch/build/scanner-paired-02-trace.jsonl` 和 `.scratch/build/scanner-paired-02-maintenance.jsonl`。
