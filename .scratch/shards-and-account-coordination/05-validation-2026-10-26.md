## Implementation

- `Gateway.sendShardBatch` admits at most four requests and one eligible command per shard in a bounded turn. It uses the same `prepareDispatch`, final proof validation and canonical request conversion as individual sends, then calls the account's sole VenueAdapter with one canonical `order_batch`. Its existing native scheduler retains transport rate limits. Priority is cancellation (including KillSwitch cleanup), Reduce-only, then opening risk; no priority bypasses qualification.
- The original request indices retain independent local results. Command identity remains in the originating shard's immutable OMS command and persisted DispatchProof: account, decision stream/domain, portfolio, order, command, revision and primary fencing generation. Repeated command identities in a single turn are rejected before any durable attempt or send. Unsupported, stale or otherwise unqualified items cannot consume the other shards' transmission slots.
- Every eligible proof commits before the batch's external effect; transport acceptance commits independently afterward. Failures leave the relevant evidence Unknown. Gateway recovery restores proofs, never a resend queue. Immediate Adapter backpressure is NotSent; the pre-attempt proof remains conservatively pinned Unknown until explicit reconciliation, matching the individual-send contract.
- `CoordinatorOwner.applyGatewayOutcome` checks the original command digest and target owner before using `Owner.apply` with an explicit account scope. Terminal and duplicate place outcomes cannot downgrade an already transmitted order. Cancel/amend outcomes use their own pending state and revision instead of inheriting the old place's order-level submitted bit.
- `dispatchClientOrderIdFromShard` includes unresolved proofs for identity lookup only. The coordinator can therefore route late normalized Venue facts after an Unknown transport result or restart. This grants no permission to resend and gives the Gateway no OMS, reservation, position or ledger ownership.
- Adapter requests now distinguish command identity from an optional explicit order identity; Gateway always supplies the OMS order ID. SimulatedVenue reports/fills and all three private Adapter link registrations preserve that order identity, including cancel command 3 targeting order 1. Simulated cancellation accepts absent quantity/price. Binance/Bybit now generate namespace/account/order-bound wire client IDs through the existing callback and return those IDs with dispatch results; their direct Adapter tests cover namespace separation.
- No persisted schema changes, new dependencies, runtime options, second Adapter, Web/CLI changes, real or Demo orders were introduced.

The additional field belongs to the in-process canonical Adapter request, not a persisted CanonicalEvent or Core payload.
