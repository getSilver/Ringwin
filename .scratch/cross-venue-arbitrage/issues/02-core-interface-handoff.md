## Question

用户要求将这三项项目接口能力交给其他会话处理；本会话只维护策略行为规格。本文件是需求、源码入口和验收交接，不表示已选择核心架构或授权交易。另一个会话接手时重新核对当前源码与工作树，不能直接沿用本文件的“缺口”结论实施重复改造。

行为依据：[合同](../strategy-contract.md)；研究输入与验收编号：[算法附录第 7 节](../algorithm-validation.md#7-当前核心接口核对)。当前领域词汇入口为根级 `GLOSSARY.md`，原 `CONTEXT.md` 已在当前工作树迁移；本文件不修改迁移内容。

## 共同边界

- 优化的是项目对策略的支持能力，不是扩大策略交易权限。禁止借机加入追踪止盈、追加仓位、自动重发 Unknown、放宽止损或延长持仓。
- `VenueAdapter` 拥有私有事件到规范事件的转换，`MarketFeedAdapter` 拥有公共行情转换；Python 不直接解释 Venue 私有字段。
- `StrategyHost` 只提出意图；核心拥有授权、风险、预留、命令、唯一经济成交及权威账本。
- 按既有 ADR0001、0007、0014 实施。若引入新的权威所有者、跨 shard 协调或难逆的持久格式决策，使用 grill-with-docs 确认取舍，再按 domain-modeling 更新 GLOSSARY/ADR。不得把设计建议直接标为 accepted。
- 本文件不替代完整策略验收；模式资格分别证明，Demo 不证明收益。未获新的交易授权不得执行真实或 Demo 下单。

## H1 双边深度与成本输入

### 已核对的触发点

`src/model/canonical_event.zig` 的 `L2BookSnapshot/L2BookDelta` 目前只有最优买卖价、可选数量及一个额外卖档；`src/market/market_projection.zig` 保存这些字段。它不足以表达通用双边多档深度，更不能证明 maker 的真实排队位置。

### 需要达到的结果

1. 向策略提供有界、带 Instrument/规则版本/源序列及可见时间证据的双边价格与数量档位；深度范围及截断必须显式。这里的“完整”是声明覆盖范围内完整，不要求无限深度或全市场订单簿。
2. 定义快照/增量的有序应用、删除档位、序号缺口、重同步、重复冲突、规则版本切换和容量溢出行为。缺失深度与零深度不能混同。
3. 核心投影、Host 输入、持久捕获与重放保持一致；历史决策不能被迟到快照重写。评估数量超出可证深度或价格保护边界时返回不足，不外推成交。
4. maker 所需主动成交、队列可观测性或条件执行资料须单列能力。补齐 L2 不等于取得队列、成交率或 maker 资格。

### 验收

- 从 `MarketFeedAdapter → CanonicalEvent → 行情投影 → StrategyInputBatch` 验证双边至少多档撮合，买卖对称、合法 tick/lots、费用后净量一致。
- 缺口、乱序、重复冲突、截断、无数量、规则切换和溢出均不生成虚假全量深度；重同步前相关新增风险保持不合格。
- 同一捕获输入与重放产生相同可见盘口；验证附录 I1、V2，并记录新事件/编码/schema 的兼容策略。

## H2 Host 双腿组输出及共同准入

### 已核对的触发点

`src/strategy/strategy_host_gateway.zig` 当前 `Decision.accepted` 为单个 `OrderIntent`，`TimeInForce` 仅 GTC/IOC。`src/trading/trading_shard.zig::originalHostIntentGroup` 构造 `count=1`；OMS 已有 `IntentGroup/applyQualifiedGroup`。因此不能用“核心存在组类型”证明 Host 跨账户双腿闭环。

### 需要达到的结果

1. 一个 `StrategyOutputFrame` 承载完整有界 IntentGroup；成员使用稳定顺序与连续 IntentSequence，并绑定同一策略身份、cursor、会话及配置证据。半组、越界组、冲突身份必须原子拒绝，不能拆成两条独立新风险请求。
2. 明确两成员 ExchangeAccount、Instrument 和 VirtualPortfolio 的验证与路由；Python 不提供权威 RiskDecision、Reservation、OrderCommand 或 ClientOrderId。
3. 共同准入覆盖两腿资金、保证金、共享资金上限和 ExchangeAccount + Instrument 占用。准入拒绝不留下半组可发送命令或新预留；已经提交后部分发送失败则保留真实事实进入安全处置，不能回滚经济成交。
4. 双 IOC 的独立发送不得等待首腿成交。Maker 请求必须表达并验证原生 Post-only；普通 GTC 不能冒充 Post-only。修复由策略在原计划约束内产生后续意图，不能误用 PartialExecutionPolicy 宣称自动补齐。
5. 将“完整组传输”“核心共同准入”“各 Venue 实际执行”分别给出证据。若当前账户/shard 所有权不支持该需求，先说明限制及架构备选，不以 Python 锁表补洞。

### 验收

- Host 公共输出路径验证双账户两成员组、旧会话、过期 cursor、重复/冲突序号、半帧及容量失败，记录每种情况下命令和预留是否产生。
- A/B 与 A/C 竞争同账户品种，只能提交一个活动占用；不同品种共享账户资金也不超用。
- 在准入、持久提交和发送边界注入故障，恢复后身份/预留/占用不丢失；第二腿发送失败不将第一腿视作未发生。
- 以公共适配输入覆盖 Fill/累计报告两种顺序、重复、迟到及归档恢复，不重复对冲；核对附录 I2–I5。

## H3 周期与模型状态恢复

策略侧S6字段语义、确定性要求、崩溃切点及S6-A至S6-P已在[状态与恢复合同](../state-recovery-contract.md)补齐，作为本节需求输入。策略数值codec/schema的具体实现仍须由H3核对现有核心格式并验证，不把文档字段清单当成已实现接口。

### 已核对的触发点

`src/strategy/strategy_host_recovery.zig::PortableState` 目前为 `accumulator/event_count` 示例。已有 checkpoint、摘要、核心 snapshot 和 Host activation 框架不能证明本策略私有状态及风险管理进度可恢复。

### 需要达到的结果

1. 明确状态清单和唯一所有者：核心保持订单/成交/资金/风险与占用事实；策略保存冻结计划、阶段与退出原因、原目标/实际匹配关联、模型状态、信号重置状态、计时证据引用及下一意图序号。引用核心事实不复制一套可写权威余额。
2. 版本化 schema 要覆盖滤波均值/协方差、预热窗口、预测标签成熟队列及监测计数；精确字段取决于最终策略模型，不应把示例累加器扩充为无边界任意对象。
3. 遵守 PortableStrategyStateJsonV1、StrategyStateDigest 与 StrategyCursor；确定统计数值的稳定编码及恢复误差标准。禁止 pickle/任意浮点 JSON 绕过合同。
4. 恢复后追赶权威事件和激活屏障，停机时间计入期限；跨机时钟证据不足不得重置计时并继续持仓。旧会话输出无效，恢复策略状态本身不授予新开仓权限。
5. 周期终结、现货残余承接、品种占用释放和锁存恢复需要与核心事实一致；Unknown、永续残仓不能被“恢复完成”清除。具体权威归属由接手会话设计，不在本文预定。

### 验收

- 在 Entering/Repairing/Holding/Exiting/Reconciling 分别 checkpoint、崩溃、恢复；核对原计划、净收益目标、时限、风险锁存、模型状态和意图身份。
- 同事件流在连续执行、不同输入批次和 checkpoint 重放下，策略摘要及意图一致；误差预算不能允许改变买卖/数量/退出决策。
- 模式/参数版本不兼容、损坏 checkpoint、缺失日志尾、旧会话和时钟不可信时拒绝错误激活；已触发退出不能恢复为 Holding。
- 账户对账、迟到成交、基础币费用及残余承接后资金与占用一致；覆盖附录 I6–I8。

## 依赖与交付顺序

- H1、H2 可先独立设计和契约验证；H3 的通用 checkpoint/激活能力可并行设计，最终字段需绑定本会话收敛后的策略状态 schema。
- H2 的占用生命周期与 H3 的恢复必须使用同一权威设计；不得两边各建一套锁表。具体拆票与阻塞边由接手会话在核对架构后制定。
- 最终策略集成依赖 H1/H2/H3 的相关合同均通过，以及策略参数/行为已冻结；项目接口施工不阻塞本会话讨论策略公式。
- 接手会话优先在本文件补源码/测试/ADR链接；不要将本会话仍待确认的策略分支标成已批准。
