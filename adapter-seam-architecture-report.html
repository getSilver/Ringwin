Architecture scout · ADR 0001 · 深模块巡检

VenueAdapter 与 MarketFeedAdapter 的接缝还没形成

ADR 0001 要求两个独立 adapter：绑定账户的执行接缝，以及可跨账户共享的公共行情接缝。 跨接缝只允许核心 CanonicalEvent。现状是：vtable 只服务 SimulatedVenue； OKX 走平行直连链；三份同名 CanonicalEvent；私有 implementation 从公共行情 module 借类型。 JSON 字段名大多仍停在 OKX decoder 内，真正的泄漏是命名、编译图、以及 Demo 稳定日志里的 okx_spot_* 记录。

ADR 0001 承诺

两个 seam：VenueAdapter（订单 / 私有账户事实 / 对账）与 MarketFeedAdapter（公共行情）。两者只输出核心 CanonicalEvent。Execution Gateway 按 ExchangeAccountIdentity 路由；行情按 Venue/订阅隔离。

窄接口深模块接缝
代码现状

src/venue_adapter.zig 是 47 行 generic vtable。MarketFeedAdapter 类型与文件均不存在。OKX 公共与私有各有自己的 CanonicalEvent，且从未翻译进 TradingShard.apply。

VenueAdapter

Interface 形状正确：start / trySend / tryDrain / stop（src/venue_adapter.zig:19-46）。Request/Output 由调用方注入，因此契约知识不在 adapter module 内。

唯一 implementation 是 trading_shard.zig 私有的 SimulatedVenue（2660-2720）。AdapterRequest 只有 order_command，没有账户/订单对账请求（2651-2658）。AdapterOutputBatch 固定「1 + 5」核心事件，不是有界 CanonicalEvent 数组。

MarketFeedAdapter

计划中的独立 interface（docs/多交易所适配方案.md:274-285）没有对应 module。公共路径的真实入口是 Decoder.ingest（okx_public_market.zig:316-356）：先 RawSink，再 JSON，再内部 CanonicalEvent。

该 Decoder 是深的（簿序列、健康、规则观察），但它不是可替换的行情接缝。核心消费的是两档 price_micros 的 L2Snapshot（trading_shard.zig:283-298, 2270-2318），与 400 档 Decimal 簿没有翻译层。

3. 深度：谁是深模块，谁是浅传递

浅

venue_adapter.zig

只转发四操作。没有 OrderCommand、CapabilityProfile、对账请求、输出事件形状。implementation 必须自带全部契约，因此几乎没有 leverage。

深

okx_public_market.Decoder

隐藏 JSON、400 档簿、seq 衔接、gap/resubscribe 健康、RawIngress。接口却是 ingest(raw bytes)，不是 MarketFeedAdapter，也无法被 SimulatedVenue 复用。

深

okx_private_reconciliation.Reconciler

隐藏 REST bootstrap 双轮稳定、WS 缓冲、seen-fact 去重、Unknown、drain 顺序。输出却是私有 CanonicalEvent，且依赖 public market 的 Envelope/Decimal/Instrument。

深

okx_order_entry

Capability 校验、限流队列、place/amend/cancel JSON codec、TargetRemaining→newSz。CapabilityProfile 被困在 OKX module（63-85），不能成为执行接缝上的窄契约。

深

okx_live_chain

replay/dry-run 碰不到 transport；Demo 资格失败关闭；响应先 RawIngress。这是副作用接缝，但不是 VenueAdapter vtable。

错位的深

okx_spot_projection

第二套订单/账本投影，直接吃 private.CanonicalEvent 并写入 journal。深度很高，但接缝错误：权威状态本应只经 TradingShard.apply。

浅 realization

SimulatedVenue

硬编码 happy-path 五条 ingress。它证明了 vtable 形状，没有隐藏任何 Venue 协议，也不能跑 OKX 契约测试。

过宽

trading_shard.zig

拥有核心 CanonicalEvent、codec、SimulatedVenue、快照、夹具，并编译绑定全部 okx_*。状态迁移本身深，接缝所有权浅且分散。

5. 加深机会（按 leverage）

不引入新 Venue、SOR、或通用 REST/WS/auth 框架。只加深已承诺的两个 adapter 接缝。

P1

单一 CanonicalEvent module，禁止 adapter 盗用该名字

今天接缝是浅的，因为三个 module 都导出同名事件。ADR 已写明 adapter 内部应叫 OkxPrivateEvent / 行情等价名。加深手段：抽出核心 CanonicalEvent 作为窄接口；OKX decoder 只产私有事件；只有翻译后的事实可进入 TradingShard.apply、journal codec、replay。

证据

核心 trading_shard.zig:492；行情 okx_public_market.zig:241；私有 okx_private_reconciliation.zig:176；方案 docs/多交易所适配方案.md:155-156。

P1

把 AdapterRequest / OutputBatch 放进 venue_adapter module，让 OKX 成为真正的 implementation

当前 interface 几乎无 depth：类型住在 TradingShard，OKX 从不实现 vtable。加深后，执行 adapter 隐藏 codec、对账、RawIngress 与未知态；核心只 trySend 规范 OrderCommand（及对账请求）并 tryDrain 核心事件。SimulatedVenue 与 OKX 走同一契约，而不是平行链。

证据

vtable venue_adapter.zig:19-29；私有类型 trading_shard.zig:2651-2660；OKX 发送 okx_live_chain.zig:61-105；方案 7.1 要求对账请求与可变长输出 docs/多交易所适配方案.md:248-261。

P2

补上 MarketFeedAdapter 窄接口，让 Decoder 做 implementation 而不是接缝本身

Decoder 已经深。缺的是独立于 ExchangeAccount 的 start/tryDrain/stop，以及把 400 档 Decimal 簿投影成核心 MarketEvent 的翻译。不要把账户 session 绑到行情生命周期，也不要把核心 L2 扩成 OKX 簿的并集。

证据

ingest okx_public_market.zig:316；核心 L2 trading_shard.zig:283-298；ADR 后果「公共行情按 Venue/订阅隔离」docs/adr/0001-...:22。

P2

切断私有 implementation 对公共行情 module 的类型借用

private / order_entry / live_chain / curl 都 @import("okx_public_market.zig") 以取得 Decimal、Instrument、EventEnvelope、RawSink。这把两个 adapter implementation 焊在同一个 module 上，破坏接缝 locality。允许一个更小的 OKX 内部 primitives module；不允许行情 Decoder 成为私有事件的类型所有者。

证据

private okx_private_reconciliation.zig:7-17；order_entry 7-8；live_chain 7-8；curl okx_curl_transport.zig:8。

P2

Demo 稳定日志停止持久化 okx_spot_* 私有 union

appendStable 把 adapter ExecutionReport/Fill/Balance 写进同一 Journal 抽象，type_id 还带 OKX 产品名。journal module 仍深且中立；被破坏的是「只有核心 CanonicalEvent 可重放」这条接缝不变量。投影应消费翻译后的核心事件，或明确标为 Venue 私有审计流，而不是权威 SemanticReplay 输入。

证据

okx_spot_projection.zig:15-18, 63-70, 224-265；acceptance 写入 okx_demo_live_acceptance.zig:269。

P3

CapabilityProfile 上移到执行 adapter 契约，而不是留在 OKX codec

这是把已存在的深知识挪到窄接口上，增加核心 leverage，而不是新框架。TradingShard 不应再为了跑测试而 @import 全部 okx_*。

6. 已经隔离、不值得立项的区域

保持
  • JSON 协议字段名没有进入 OMS、TradingShard payload、StrategyHost、Python。
  • journal.zig Record 不认识 Venue。
  • Host IPC 事件集与 OrderIntent 使用 identity + micros，无 instId。
  • 两边 decoder 都先 RawIngress 再解析。
  • okx_live_chain 在 replay/dry-run 拒绝真实 transport。
  • SimulatedVenue 与 OKX 传输路径尚未混用同一连接对象。
  • venue_adapter 四操作形状与 ADR/方案一致，应保留而不是另起一套。
明确不做
  • 不新增 Venue implementation。
  • 不做 SOR / 跨 Venue 拆单。
  • 不把 curl/auth/JSON 抽成通用 plugin 框架（ADR 已否决）。
  • 不把核心 CanonicalEvent 做成 OKX 字段并集来「补覆盖率」——那会把泄漏合法化。

巡检结论：ADR 0001 的接缝决定仍然正确。缺口不是缺框架，而是 adapter 虽深、接缝仍浅——核心从未只通过一个 CanonicalEvent 接口面对 Venue。
