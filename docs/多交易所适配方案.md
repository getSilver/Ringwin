# 多交易所适配方案调研

> 面向 RingWin 现货/永续多策略交易核心的多交易所（Binance / Bybit / OKX）适配方案。
> 调研岗产出：每条结论标注 **已证实**（有源码/文档一手来源）或 **建议**（我的方案判断，供决策讨论）。
> 调研日期：2026-08-27 | 来源：本机工作树源码 + `docs/` 既有分析

---

## 一、现状盘点（已证实）

### 1.1 当前唯一真实交易所适配器是 OKX，且为"固定 OKX Demo 垂直链"
`src/okx_live_chain.zig:1` 声明为
> "Side-effect boundary for the fixed OKX Demo vertical chain."
- 行动态/账户/订单都是 OKX 具体 JSON 解析模块：
  - 公共行情 `src/okx_public_market.zig`（`Decoder`、L2、标记/指数价、资金费率）
  - 私有对账 `src/okx_private_reconciliation.zig`（订单/成交/余额/持仓/保证金快照）
  - 订单录入 `src/okx_order_entry.zig`（`OrderCommand`、调度、编码）
  - 认证 `src/okx_rest_auth.zig`
- 这些模块**没有**任何通用化抽象，字段名直接使用 OKX 命名（`instId`、`clOrdId`、`fillPnl` 等），且**不依赖** `venue_adapter.zig`。

### 1.2 已存在一个通用适配器接口，但只被测试用 SimulatedVenue 使用（已证实）
`src/venue_adapter.zig:19` 定义了运行期 vtable 接口：
```
Interface(Request, OutputBatch): start / try_send / try_drain / stop
```
- 该接口当前**只被实例化一次**：`src/trading_shard.zig:2539` `VenueAdapter = venue_adapter.Interface(AdapterRequest, AdapterOutputBatch)`，且只用于 `SimulatedVenue`（`trading_shard.zig:2541`，测试用假交易所）。
- OKX 各模块（`okx_live_chain` / `okx_public_market` / `okx_private_reconciliation` / `okx_order_entry`）**均未实现该 vtable** —— 见 grep：`venue_adapter.Interface`/`VenueAdapter(` 仅出现在 `trading_shard.zig`。
- 接口的请求/输出类型已以**核心事件**为边界（已证实，`src/trading_shard.zig:503` `const InputEvent = CanonicalEvent;`）：
  ```
  AdapterRequest      = union { order_command: OrderCommand }          // 2530
  AdapterOutputBatch  = { dispatch_result: InputEvent, ingress: [5]InputEvent }  // 2534
  ```
  → 设计意图上，适配器上送的就是核心 `CanonicalEvent`，但该意图目前只在 SimulatedVenue 中落实。

### 1.3 存在两套并行的"CanonicalEvent"事件模型（已证实）
- **核心层**：`src/trading_shard.zig:23` 的 `CanonicalEvent` + `Payload` 联合体（36 种事件标签），schema_version=4，是跨策略/适配器/日志/重放的规范消息。
- **OKX 适配器本地**：各自定义了自己的 `CanonicalEvent`/`EventPayload` 联合体：
  - `src/okx_public_market.zig:241`（行情：instrument_definition / l2 / reference_price / funding）
  - `src/okx_private_reconciliation.zig:176`（私有：execution_report / fill / balance / position / margin）
- 这两套是**不同结构**：适配器层字段远比核心层丰富，但适配器→核心桥接不完整（此为 `docs/canonical_event_field_coverage.md` 的核心发现：OKX 适配器层覆盖 ~85%，核心层 ExecutionReport/Fill 仅 ~40%）。

### 1.4 已验证的时序/证据优势（已证实）
RingWin 在适配器边界保留了原始证据链：`RawSink` 先把每个原始 frame 追加（`okx_public_market.zig:87`），再解析/变更状态，事件携带 SHA-256 `content_hash`、sequence、多维时间戳（source/receive/monotonic/wall）。这是可在多交易所上延续的差异化能力。

## 二、方案判断（建议部分）

一个核心结论先行：**先定义并补足单一规范边界（核心 `CanonicalEvent` + `venue_adapter.Interface` 契约），再接入第二个交易所。** 不要在还没有统一规范模型时并行添加 Binance/Bybit，否则会像 OKX 一样把每家的私有 `CanonicalEvent` 复制一份，桥接缺口将进一步扩大。

### 2.1 核心结论
**把 `src/venue_adapter.zig:Interface` 确立为唯一的交易所适配签名，并让所有交易所适配器在边缘把私有事件翻译成核心 `trading_shard.zig:CanonicalEvent`；在接入第二个交易所之前，先把核心事件模型的覆盖率缺口补齐。**

理由是已证实的两条事实链：
1. 适配接口与"上送内容=核心事件"的意图**已经存在但只有模拟实现**；
2. 唯一真实适配器 OKX 明明有丰富事件，却**绕过了这个契约**、维护自有一套私有 `CanonicalEvent`，造成"适配器层 ~85% / 核心层 ~40%"的桥接落差。

若现在不先统一契约就并行加 Binance/Bybit，只会再把"各揣一套私有 CanonicalEvent"的模式复制三份，桥接落差从 1 处变成 3 处。**先修契约，再加交易所。**

### 2.2 分步建议

**第 0 步：补足核心事件模型（前置，见 `docs/canonical_event_field_coverage.md` 行动项 P0/P1）**
在核心 `ExecutionReport` / `Fill` / `Balance` / `Position` / 状态枚举上补齐三所共通的字段，使核心模型成为三者的"真超集"（对齐 Nautilus 参考标准）：
- 订单生命周期时间戳、`expired` / `rejected` 状态
- 触发/算法单字段（trigger_price/type、tp/sl、trailing）
- 持仓方向与保证金模式（position_side / margin_mode / leverage）
- 成交粒度费用与盈亏（fill_fee/ccy、rebate、realized_pnl）
- 跨通道序列（seq / prev_seq_id），供多通道绝对排序
> 因为核心模型是所有策略/日志/重放/风控共享的规范消息，这里"一次补到位"成本最低；每新增一家交易所只需做一次映射，而不是为每家各自修补。

**第 1 步：把 OKX 重构为第一个走该契约的实现**
把 `okx_public_market` + `okx_private_reconciliation` + `okx_order_entry` 组织为一个 `OkxAdapter`，实现 `venue_adapter.Interface` 的 vtable，并在边缘把 OKX 私有事件桥接成核心 `CanonicalEvent` 后从 `try_drain` 上送。
- 这一步的价值：既验证"适配器=纯翻译层"这一 seaming 是否成立，又把 OKX 现有工作从"游离私有模块"迁移进共享契约，避免遗留双事件模型。
- OKX 认证/签名（`okx_rest_auth.zig`）与 RawSink 证据链**保留在适配器内部**，不进核心层。

**第 2 步：为 Binance、Bybit 各写一个实现同一契约的适配器**
此时每新增一家交易所的工作量 = "换 JSON 解析 + 换认证/传输 + 映射到核心事件"，共享 start/stop/backpressure/drain 生命周期与上游消费路径，不再各起炉灶。

**第 3 步（建议但非必须）：把公开行情流也纳入边缘翻译**
当前公开行情走完全独立的 `okx_public_market.Decoder`（`IngressBatch`，`okx_public_market.zig:255`）。多所化时需要一个明确决策：行情与执行/账户各自独立地"解析→翻译成核心事件→上送"。建议统一在适配器边缘翻译成核心 `l2_snapshot` / `l2_delta` / `mark_price` / `funding_settlement`，使 OMS/风控/策略只面对一份行情事件语言。

### 2.3 边界与需要明确的范围限制（建议）
- **不要统一做初始化层**：各交易所的 REST/WS transport、认证与签名、API 网关路径差异大，统一抽象收益低、风险高。让它们留在各适配器内部，只有"上送的核心事件"跨边界共享。
- **不要强求字段等价**：核心模型字段应设可空/可选，覆盖"三所表达的并集"；某所没有的字段（如个别费用模型）置 null，不强行编造。
- **行情与执行的合并/分离需要显式决定**：`venue_adapter.Interface` 当前是"执行形状"（send 请求→drain 输出），而公开行情是单向推流。是否把二者都汇入同一适配器契约、或为行情单开一条 Feed 契约，是架构上要先敲定的一个决策点（我倾向行情走同一适配器的 ingress 上送，复用 backpressure 与证据链，但需要团队确认）。

## 三、与既有分析的对齐
- 本方案的"先补核心模型→再把适配器桥接到核心"顺序，直接继承 `docs/canonical_event_field_coverage.md` 的核心发现：**适配器层字段覆盖度高、核心层低，差距在桥接**。本方案把这一"差距"转化为"先做哪一步"的实施次序。
- 本方案的"三所并集/可空字段"原则，与 `docs/1canonical_event_field_coverage.md` 逐所字段对比中"某所独有的字段"一节一致。

---

## 四、结论（一句话）
多交易所适配应采用 **"单一规范边界（核心 `CanonicalEvent` + `venue_adapter.Interface`）+ 适配器纯翻译层（私有解析/认证留在内部、边缘翻译成核心事件）"**，并且 **先补齐核心事件模型覆盖、让 OKX 成为首个走该契约的实现，再横向复制到 Binance/Bybit**，而不是在没有统一事件边界前并行堆三套私有模型。
