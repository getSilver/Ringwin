# RingWin 多交易所适配落实方案

> 状态：已接受，进入实施
> 生效日期：2026-08-28
> 正式目标：OKX、Binance、Bybit 的现货与线性永续
> 首个交付：OKX 统一接缝 + Binance BTC-USDT 现货/USDT 线性永续 Demo/Testnet 闭环
> 字段基线：`docs/canonical_event_field_coverage.md`
> 架构决策：`docs/adr/0001-separate-venue-execution-and-market-feed-seams.md`

本文取代 2026-08-27 的《多交易所适配方案调研》。多交易所现为 RingWin 正式目标；
README 中“停止继续扩展 Adapter”的旧路线不再代表当前决策，必须在波次 0 同步修订。

## 1. 结果与实施顺序

RingWin 建立两个稳定 seam：

1. `VenueAdapter` 位于 Execution Gateway 与 Venue/SimulatedVenue 之间，负责订单发送、
   私有订单与成交事实、账户事实和对账。
2. `MarketFeedAdapter` 位于公共行情连接与市场事实入口之间，负责产品定义、L2、参考价、
   资金费率和行情健康事实。

核心只拥有一套 `CanonicalEvent`。每家 Venue 的认证、transport、JSON codec、限流和恢复留在
各自 Adapter implementation 内，跨 seam 前必须翻译成规范事件。Venue 私有但不构成核心事实的
字段保留在 RawIngress。

实施顺序固定为：

1. 修复构建与文档基线；
2. 建立共享身份、规范事件、能力剖面和两个 Adapter 契约；
3. 让 OKX 成为首个真实契约实现；
4. 默认接入 Binance 作为第二实现并验证 seam；
5. 接入 Bybit；
6. 独立完成 Linux 生产性能与部署资格。

若产品优先级要求 Bybit 先于 Binance，只交换波次 4、5 的 Venue，不改变前序契约工作。

## 2. 当前基线

当前 OKX Demo 已证明一条真实 Venue 垂直链，但设计意图与实现仍分裂：

- `src/venue_adapter.zig` 已定义 `start / try_send / try_drain / stop` vtable；
- `AdapterRequest`、`AdapterOutputBatch` 和 `VenueAdapter` 实例类型仍私有于
  `src/trading_shard.zig`；
- 只有 `SimulatedVenue` 实现该 vtable；
- `okx_order_entry.zig`、`okx_live_chain.zig` 和 `okx_private_reconciliation.zig` 组成
  绕过该 vtable 的 OKX 私有执行链；
- `okx_public_market.zig` 与 `okx_private_reconciliation.zig` 各自声明名为
  `CanonicalEvent` 的私有事件；
- OKX decoder 已保留 client order ID、平均成交价、费用资产、流动性、盈亏和账户快照，
  核心 `ExecutionReport` / `Fill` 尚未完整承载；
- `Instrument` 仍硬编码为 `btc_usdt_spot` 和 `btc_usdt_swap`；
- `trading_shard.zig` 混合规范事件、状态机、快照、SimulatedVenue、测试夹具和 benchmark；
- 仓库缺少 `build.zig` 和 README 已链接的 MIT `LICENSE`。

在上述问题闭合前，不开始 Binance 生产实现，避免复制一套新的私有事件和核心分支。

## 3. 目标架构与依赖

```text
Public Venue Feeds
        │
        ▼
 MarketFeedAdapter ──────────┐
                             │ Canonical MarketEvent
                             ▼
                       TradingShard
                             │
StrategyHost ─► OrderIntent ─► Risk ─► OMS ─► OrderCommand
                                                     │
                                                     ▼
                                             Execution Gateway
                                                     │
                                         ExchangeAccountIdentity 路由
                                             ┌───────┼───────┐
                                             ▼       ▼       ▼
                                           OKX    Binance  Bybit
                                             │       │       │
                                             └───────┴───────┘
                                          Canonical Venue/ExecutionEvent
```

允许的依赖：

```text
TradingShard / OMS / Gateway -> canonical_event / venue_adapter / market_feed_adapter
OKX / Binance / Bybit        -> canonical_event / venue_adapter / market_feed_adapter
具体 Adapter                 -> 自己的认证、transport、codec、reconciler
```

禁止的依赖：

```text
TradingShard / OMS / Gateway -> okx_* / binance_* / bybit_*
CanonicalEvent               -> Venue JSON 类型、字段名或错误码
Strategy                     -> Venue 私有能力或 endpoint
Adapter                      -> Risk、OMS、账本或 VirtualPortfolio 可变状态
```

每个 `VenueAdapter` 实例固定绑定 `Venue + Environment + ExchangeAccount + TradingCredential`。
Execution Gateway 使用启动期固定的 `ExchangeAccountIdentity -> VenueAdapter` 路由，不使用动态
插件加载，不按字符串 Venue 名称分支，也不做跨 Venue 自动择优或拆单。

公共行情连接可跨账户共享；其隔离范围是 `Venue + Environment + SubscriptionSet`。

## 4. 共享身份与数值模型

### 4.1 身份

| 身份 | 含义 | 规则 |
|---|---|---|
| `VenueIdentity` | Venue 注册身份 | 稳定整数，永不复用 |
| `AssetIdentity` | 可持有、结算或计价的 Asset | 不使用 Venue 币种字符串作身份 |
| `ExchangeAccountIdentity` | 真实交易账户 | 沿用现有 `u128` 领域身份 |
| `InstrumentIdentity` | 某 Venue 上的具体产品 | 同资产对在不同 Venue 是不同 Instrument |
| `OrderIdentity` | RingWin Order | 不随改单、重连或恢复改变 |
| `ClientOrderId` | RingWin 发给 Venue 的客户端标识 | 固定容量字节串，由能力剖面验证 |
| `VenueOrderRef` | Venue Order 标识 | `VenueIdentity +` 最长 64 字节 opaque 值 |
| `VenueTradeRef` | Venue Fill 标识 | `VenueIdentity +` 最长 64 字节 opaque 值 |

核心不再假设 Venue order/trade ID 是 `u64`。Venue symbol 只是版本化映射，不是权威身份。

`InstrumentDefinition` 至少包含 Venue、Venue symbol、产品类型、base/quote/settlement Asset、
linear/inverse、contract value、tick、lot、最小数量/名义价值和交易状态。Adapter 观察到变化只
产生 `InstrumentDefinitionObserved`，经验证的 `ConfigEvent` 在明确 barrier 激活后才改变
`InstrumentRules`。

### 4.2 数值

- Venue 文本先无损解析为 `Decimal { coefficient: i128, scale }`，禁止浮点；
- `AssetDefinition` 固定每个 Asset 的原子精度；
- `InstrumentRules` 固定 price/quantity scale、tick、lot、contract value 和结算公式；
- 跨 seam 前转换为带 Asset/Instrument 与 RulesVersion 的整数 `AssetAmount`、`Price`、
  `Quantity`；
- 无法按当前规则精确表示的 Venue 数值失败关闭，不在 Adapter 静默舍入；
- 风控、OMS、账本继续使用 checked integer arithmetic；
- `price_micros`、`fee_micros` 等固定 USDT 六位模型在迁移中替换，不能成为多资产公共契约。

## 5. CanonicalEvent

### 5.1 原则

`CanonicalEvent` 是跨核心模块的规范不可变消息，不是 Venue 字段并集，也不是直接持久化的
进程 ABI。稳定日志继续使用显式 codec；当前开发阶段尚未形成受支持恢复基线，允许直接修改
现有 provisional schema、快照、fixture 和固定摘要，不保留 v4 兼容。首个多 Venue 恢复基线
发布后，新增字段与语义再遵守 `StableEventSchema` 的版本规则。

公共 envelope 至少提供：

- EventType、SchemaVersion、EventIdentity 与 SourceFactIdentity；
- Venue、ExchangeAccount（账户事实）和 Instrument/Asset（产品或资产事实）；
- VenueSourceStreamIdentity、VenueSourceSequence 及可用的 previous/cross sequence；
- source、receive、monotonic、wall/audit 时间和存在位；
- AdapterSessionIdentity、bootstrap snapshot identity 与 RawEvidenceRef。

各 Venue decoder 可以保留内部强类型事件，但命名为 `OkxPrivateEvent`、
`BinanceMarketEvent` 等；只有跨 seam 的规范事实可以命名为 `CanonicalEvent`。

### 5.2 ExecutionReport 与 Fill

两者职责严格分离：

```text
ExecutionReport
  OrderIdentity / VenueOrderRef / ClientOrderId
  InstrumentIdentity / ExchangeAccountIdentity
  OrderRevision / side / order type / time in force
  status / reject reason
  original / cumulative / remaining quantity
  limit price / average fill price
  portfolio reduce-only / venue reduce-only
  position side / margin mode / leverage
  venue create/update time

Fill
  OrderIdentity / VenueOrderRef / VenueTradeRef / ClientOrderId
  InstrumentIdentity / ExchangeAccountIdentity
  side / quantity / price
  fee / fee asset
  rebate / rebate asset
  realized PnL / settlement asset
  maker/taker
  venue fill time
```

Venue 在订单频道附带 last fill 字段时，Adapter 必须按 `VenueTradeRef` 去重并产生独立 `Fill`。
`OrderState` 由 OrderCommand、ExecutionReport 和 Fill 投影；账本、仓位和费用只能由唯一 Fill
或 `VenueForcedExecution` 驱动，不能从 ExecutionReport 重复入账。强平和 ADL 不伪造成普通
Order/Fill。

### 5.3 完整快照与单项绝对观察

账户事实从开始同时支持完整快照和增量观察：

```text
ExchangeBalanceSnapshot     完整 Asset 余额集合
ExchangeBalanceObserved     单个 Asset 的最新绝对余额观察
ExchangePositionSnapshot    完整真实持仓集合
ExchangePositionObserved    单个 Instrument + PositionSide 的最新绝对持仓观察
ExchangeMarginSnapshot      完整账户/逐仓保证金集合
ExchangeMarginObserved      对应范围的最新绝对保证金观察
```

`Observed` 事件使用绝对值而不是数值差，携带 Venue、账户、Asset/Instrument、source session、
source sequence、Venue 时间、依赖的 bootstrap snapshot 和 upsert/removed 语义。重复事件因此
可幂等处理。

核心只有在完整 bootstrap snapshot 已应用且后续来源序列连续时接受 Observed；断档、回退或
冲突使对应账户投影失效，关闭 SafetyGate 并重新执行账户对账。Snapshot 只能表示明确范围、
游标和时点下的完整集合，局部 WS 消息不能冒充 Snapshot。

### 5.4 行情事实

首个交付规范化：

- `InstrumentDefinitionObserved`；
- `L2BookSnapshot` / `L2BookDelta`；
- `ReferencePrice`（mark/index 明确区分）；
- `FundingRatePublished`；
- `MarketDataHealthChanged`；
- 已有产品范围内的公开 `MarketTrade`（实际订阅时）。

行情 gap 后只有新的完整 L2 snapshot 能恢复健康，不能用后续 delta 猜测补洞。

## 6. Venue 来源顺序与恢复屏障

不要求所有 Venue 提供跨通道全局序列，也不按 Venue 时间戳伪造绝对顺序：

- 每个 REST/WS 来源拥有稳定 `VenueSourceStreamIdentity` 和独立 `VenueSourceSequence`；
- Venue 提供 cross sequence 时原样保留，但不是所有 Adapter 的必填能力；
- Adapter 先完成 REST bootstrap，再按确定规则释放期间缓冲的 WS 事实；
- 核心按 Adapter 输出的本地 ingress sequence 应用；
- Venue 时间只作证据、延迟和冲突判断；
- 同一 SourceFactIdentity 出现矛盾内容时停止增量应用并重新对账，不猜测先后。

## 7. Adapter 契约

### 7.1 VenueAdapter

保留当前四操作 interface 形状：

```zig
start(config)                 !void
trySend(AdapterRequest)       !SendResult
tryDrain()                    !?AdapterOutputBatch
stop(DrainDeadline)           !void
```

`AdapterRequest` 从开始覆盖三类真实职责：

```text
OrderCommand
OrderReconciliationRequest
AccountReconciliationRequest
```

启动 bootstrap 和断线恢复可以内部触发，但必须复用显式账户对账 implementation。
`CancelAll` 不作为 Venue 特殊请求；核心为已知未完成 Order 生成逐订单 Cancel OrderCommand。
凭证轮换和环境变化通过新 Adapter session 切换，不加入任意管理命令。

`AdapterOutputBatch` 是有界 CanonicalEvent 数组加有效长度，不再固定为“一个 dispatch + 五个
ingress”。所有请求结果经 `tryDrain()` 返回。

接口不变量：

- 队列、批次、分页和原始帧尺寸有界；
- trySend/tryDrain 不隐藏阻塞或分配；
- 每次 OrderCommand 发送尝试恰好产生一个 `OrderDispatchResult`；
- 未发送、已提交和 Unknown 严格区分；
- Unknown 不自动重发；
- Venue 响应先提交 RawIngress，再解释为规范事实；
- replay、dry-run 和未获资格环境无法触达真实 transport；
- stop 必须 drain，未完成时失败关闭。

### 7.2 MarketFeedAdapter

公共行情使用独立 interface：

```zig
start(MarketFeedConfig)       !void
tryDrain()                    !?MarketEventBatch
stop(DrainDeadline)           !void
```

订阅集合在启动配置中固定，通过新配置版本和 session 切换变更；首波不增加动态订阅命令。
重连、重新订阅和快照恢复属于 implementation，但必须输出明确的健康事实。

### 7.3 Session、版本与配置

- Adapter session 内 Venue、Environment、ExchangeAccount 和 TradingCredential 不可原地更换；
- 凭证轮换或 endpoint/environment 改变创建新 session；
- 新 session 先用 ObservationCredential 完成只读 bootstrap，再经受控切换获得发送资格；
- InstrumentRules、CapabilityProfile、限流和规范化政策可以生成新版本；
- 新版本先观察、验证并记录内容哈希，再由 ConfigEvent 在 ShardBarrier 激活；
- OrderCommand 固定携带 capability/rules/config/session 版本，发送前不一致即拒绝；
- 旧 session 失去发送资格后保持只读对账，直到未完成订单和 Unknown 闭合。

## 8. CapabilityProfile 与字段处置

`CapabilityProfile` 从 OKX 私有类型提升为公共执行契约，绑定：

```text
Venue + Environment + ExchangeAccount + Product/Instrument scope
CapabilityVersion + RulesVersion + ConfigVersion + QualificationEvidence
```

至少声明：

- place/amend/cancel/batch 和逐项结果；
- Limit、Market、IOC、FOK、Post-only；
- 原生 amend 与 TargetRemainingQuantity 转换；
- VenueReduceOnly、持仓模式、保证金模式和价格保护；
- ClientOrderId 格式、幂等查询和 Unknown 对账范围；
- Venue/账户/产品级限流、分页和可见性延迟；
- Demo/Testnet/Production 的独立资格状态。

缺失能力默认拒绝；NonDegradableCapability 不得本地模拟；非原地 amend 只能在明确授权后走
CancelConfirmCreate；PendingCancel 或 Unknown 阻止替代订单；Adapter 不得修改 OrderIntent、
重新风控或自行选择 Venue；原始错误码只作证据，核心只消费 CanonicalRejectReason。

`docs/canonical_event_field_coverage.md` 在波次 1 改成逐字段处置矩阵。每个官方字段必须归入：

| 处置 | 含义 |
|---|---|
| Canonical | 跨 Venue 稳定领域事实，进入核心事件 |
| AdapterInternal | 认证、分页、去重、排序或协议状态 |
| RawEvidence | 保留审计，但核心不消费 |
| Unsupported | 当前产品范围拒绝并关联能力规则 |
| NotApplicable | 不适用于现货/线性永续范围 |

每个 Canonical 字段记录目标事件、类型、单位、必填条件和缺失处理。完成证明不再使用简单覆盖率。
首波不实现算法单、OCO、止盈止损、追踪止损、STP 和期权；这些能力出现真实 OrderIntent 与
Adapter implementation 时再定义对应事件，不能通过预留大量 optional 字段宣称支持。

## 9. 隔离与安全

- 执行队列、输出队列、健康状态和 SafetyGate 至少按 ExchangeAccount 隔离；
- 公共行情队列至少按 Venue/订阅分片隔离；
- 某账户输出满只关闭该账户新增风险并触发对账；
- 某 Instrument 行情断档只关闭依赖该产品的 OpeningGate；
- 认证失败、Unknown 或私有流断档提升到对应 ExchangeAccount 的 LatchedSafetyGate；
- 全局 Gate 只用于共享权威设施失败，如 journal 不可写或主身份失效；
- Router 每轮为各 Adapter 设置有界预算，繁忙 Venue 不能饿死其它 Venue；
- 一个 ExchangeAccount 同时只有一个持有效 FencingToken 的发送主实例；
- 真实凭证禁止提现，并绑定唯一 Venue、账户、环境和用途。

## 10. 模块落位与 TradingShard 拆分

首波使用最少新增公共模块：

```text
src/canonical_event.zig       共享身份、数值和规范事件
src/venue_adapter.zig         执行契约、能力剖面与规范化政策
src/market_feed_adapter.zig   公共行情契约
src/okx_adapter.zig           组合现有 OKX implementation 并完成翻译
```

现有 OKX auth、curl transport、order entry、live chain、private reconciliation 和 public market
保持 Venue 私有 implementation，不统一 transport。

`trading_shard.zig` 只做行为保持的增量拆分：

1. 提取规范事件、身份和数值；
2. 提取两个 Adapter 契约及 SimulatedVenue；
3. OKX 统一 seam 通过后提取 snapshot codec；
4. 移出测试夹具、固定摘要和 benchmark；
5. `TradingShard.apply(CanonicalEvent)` 始终是唯一公开状态迁移 interface；
6. 不把每种事件 handler 拆成浅模块。

schema 并补全三家映射，后者先修契约，禁止核心 Venue 条件分支。

### 波次 5：Bybit Demo/Testnet

重复波次 4 的完整资格流程。Bybit 完成后，公共契约视为经三个真实 implementation 验证。

### 波次 6：生产账户与部署资格

分别完成生产 API 资格、凭证托管、Observation/ExecutionCredential 切换、单活热备、fencing、
发布、排空、恢复和人工授权。Demo/Testnet 结果不能自动升级为生产资格。

### 波次 7：Linux 性能资格

该波次独立测量四个 TradingShard 独立物理核、Router/I/O/StrategyHost/系统外围容量、CPU
affinity、NUMA、中断、真实 TLS、RawIngress、journal 写入/fsync、稳态、突发、慢消费者和断连
恢复，输出 P50/P99/P99.9、吞吐、队列水位、丢弃、恢复时长和正确性摘要。

“五核”只是最低候选拓扑，不是永久合同。io_uring、epoll、专用日志线程或批量同步由测量决定。
Windows 只作开发回归，交叉编译只证明可构建。

## 12. 契约测试矩阵

每个 VenueAdapter 运行同一套测试：

| 类别 | 必测行为 |
|---|---|
| 生命周期 | start 重复、未启动 send/drain、stop drain、stopped |
| 背压 | 请求满、输出满、公平预算、无丢失、无无界分配 |
| 订单 | place、amend、cancel、逐项 batch、版本过期 |
| 身份 | ClientOrderId 稳定、opaque Venue ref、重复事实幂等 |
| 回报 | accepted、partial、filled、canceled、rejected、amended |
| 成交 | report/fill 乱序、重复 fill、费用资产、返佣、maker/taker |
| 账户 | 完整 snapshot、绝对 observed、removed、bootstrap 依赖、断档 |
| Unknown | 三态区分、禁止自动重发、订单与账户完整对账 |
| 恢复 | REST 分页、WS 缓冲、稳定屏障、迟到事实、ConfirmedAbsent |
| 证据 | RawIngress 先于解析、hash/时间保留、损坏失败关闭 |
| 重放 | 无网络副作用、最终状态摘要一致 |

每个 MarketFeedAdapter 运行：产品定义、L2 snapshot/delta、gap/regression/conflicting duplicate、
mark/index/funding、RawIngress 顺序、背压、重连及新 snapshot 恢复健康。

Venue codec 另保留官方 fixture 单元测试；契约测试不依赖网络。真实 Demo/Testnet 验收必须显式
启用、限制名义价值、禁止提现权限并执行前后清理。

## 13. 发布与故障处理

- 新 Adapter 默认只读，完成配置、余额、仓位、保证金、未完成订单和 Unknown 屏障后进入 Ready；
- 交易由 SystemOwner 显式 EnableTrading，不能因配置存在而自动开启；
- Adapter 认证失败、序列缺口、证据不可写、输出阻塞或对账不完整时失败关闭；
- 新旧 Adapter 并行验证只允许旁路只读比较，禁止两个 implementation 同时发送；
- 发布回退遵守正向版本切换，不回滚权威 Order、账本、仓位或快照。

## 14. 非目标

- Smart Order Routing、跨 Venue 拆单或自动择优；
- 跨 Venue 净仓、资金共享或统一保证金；
- 动态插件、脚本化 Adapter 或通用 REST/WS/auth 框架；
- 期权、交割、组合保证金、跨分片原子多腿；
- 算法单、OCO、止盈止损、追踪止损和 STP 的首波实现；
- Adapter 自动重试 Unknown 或按错误文本猜测降级。

以上能力出现明确 OrderIntent、领域事实和资格标准后另立波次，不能靠预留 optional 字段宣称支持。

## 15. 总体验收定义

1. OKX、Binance、Bybit 各有真实 VenueAdapter 和 MarketFeedAdapter implementation；
2. 三家通过相同契约测试；
3. TradingShard、OMS、Risk、Economics、Journal 和 StrategyHost 不含 Venue 条件分支；
4. Venue 私有字段只存在于各自 implementation 和 RawIngress；
5. 字段处置矩阵覆盖首波官方消息的每个字段；
6. CapabilityProfile 能解释全部支持、拒绝和明确降级路径；
7. 任一 Venue 断连、限流、Unknown、账户或行情 gap 不破坏其它 Venue/分片；
8. live 与 replay 对同一规范事实得到相同最终状态摘要；
9. Demo/Testnet、生产账户、Linux 性能资格证据严格分离；
10. 构建入口、文档、LICENSE、Zig 版本和验收命令一致。

在波次 2 完成前不得开始 Binance 实现；在波次 4 通过前不得为 Binance 开放真实生产下单；
在波次 7 通过前不得把 Windows 或交叉编译结果表述为生产性能资格。
