# 跨所价差套利从扫描到交易的业务审计与优化建议

2026-11-19。操作目标是从空配置开始，在前端选择两腿市场、产品、环境和排除币种，扫描可交易机会，人工将选中的路线加入策略，由策略开仓、管理敞口、退出并对账。当前默认入口无法走完整个周期。下文的目标行为来自本次业务确认，实施和运行验收仍待完成。

## 市场选择、资产和收益

| 环节 | 当前断点 | 目标与验收 |
|---|---|---|
| 交易所设置与范围 | 当前前端账户表单仅更新 React 状态。后端已有持久设置与范围筛选；页面批量添加取交易所和产品的笛卡尔积，任一来源缺产品或缺某个排除币就会中断。 | 接回设置读写接口，目录按已注册适配器提供实际可选交易所、产品、环境。用户逐腿选择，也可批量添加可选项。排除币只影响拥有该币的来源。空目录从页面保存、刷新、重登后仍可启动同一范围。 |
| 产品与环境配对 | 设置枚举、公共 transport、候选生成、核心批准分别写有场所、环境或产品条件。当前同环境比较会过滤 Demo × Testnet，双现货仅观察，现货配永续仅生成一个方向。 | 用户选定的任意可选交易所、产品和环境组合都进入匹配。移除后端针对用户组合的准入校验及写死的配对表。两腿各自保留 Venue、产品、请求环境、实际行情来源和账户，适配器依该腿路由。目录动态增加第三个 Venue 或产品时无需修改配对代码。覆盖 Demo × Testnet、反向选择、同类和异类产品；执行能力或库存欠缺时显示具体腿与原因。 |
| 核心资产关联 | 默认 Web 未注入核心资产投影，未登记的同名币被赋予不同来源身份，两个盘口可能产生零候选。 | 从核心投影读取两腿共同敞口资产及报价资产关联，保留资产身份、单位、倍率、来源与版本。缺登记时显示具体缺项。以两个同名异资产、两个异名同敞口、缩放合约和登记变更重启验证，旧关联失效后重新配对。 |
| 费用与经济评估 | 页面费率未进入策略。扫描依赖节点发布的模型、资金、风险和逐腿费用包；当前费用包有到期检查，进程重启会改变评估时钟身份。正盘口价差仍可能被完整周期成本否决。 | 用户按账户及适用产品手动维护 Maker/Taker 费率，保存后持续生效，直至手动修改。移除费率的生效时段、TTL 和到期拒绝。保留版本、费用币种及百分比到 ppm 的精确转换。扫描与开仓前复核取同一版本；改费后重算候选，旧决策可按原版本重放。费率缺失给出提示，成交后按实际收费或返佣入账。节点在启动和输入变化时供应其余评估材料，分别报告缺模型、资金、风险或行情；验证重启后费率仍可用。 |
| USDT/USDC | 当前扫描会拒绝报价和结算资产不同的腿，核心也要求两腿结算资产相同。 | 项目内部跨所比较、扫描净收益与策略决策对 USDT/USDC 按 1:1 处理。按原币保留数量以便算汇差。扫描记录预估汇差，策略记录实际敞口对应的汇差，收益报告单列，避免在内部 1:1 收益中重复扣加。其他报价资产依核心关联处理。 |

汇差建议统一用 USDT 展示，保存行情来源、采样时刻和方向。例如 1 USDC = 0.998 USDT，净收 1,000 USDC 相对内部平价的估值差为 −2 USDT，净付同额则为 +2 USDT。对持有期间的汇差按有符号持仓及两次汇率之差计算，同一余额在相同汇率下反复采样不会重复产生损益。按决策、成交和退出时点保存引用，缺汇率时汇差显示待补，内部估值仍按平价。此处重开 ADR 0022 中关于内部损益不得固定 1:1 汇总的约定，原因是用户已指定内部比较口径及独立汇差归因。实际余额、费用币种和场所对账仍须可追溯，实施时应同步修订相应财务合同与 ADR。[ADR 0022](../adr/0022-separate-margin-model-from-settlement-asset.md)

## 广域扫描优化方案

当前有 16 个活跃品种上限。各品种串行请求盘口，默认盘口最大年龄 5 秒、两腿最大时间差 1 秒。单会话原始捕获预算 4 MiB，运行目录达到 64 MiB 会阻止新来源。只调高 16 的数值会加长轮询周期，并加速耗尽存储。[订阅、轮询与捕获](../../python/opportunity_scanner/scanner_runtime.py) · [时效判定](../../python/opportunity_scanner/scanner_console.py)

1. **在订阅前缩小数据量。** 用完整目录与核心资产投影求用户范围内可组成的路线，先应用产品及排除条件，同一盘口只订阅一次。支持批量报价的适配器可用轻量报价做粗筛，候选再取双腿深度；粗筛结果标明等待深度验证。
2. **按交易所调度。** 复用适配器支持的批量或 WebSocket 订阅；仅提供 REST 的来源按各自限频、有界并发、退避和公平轮转。把候选两腿安排在接近的采样时间。单所限流只降低受影响路线的新鲜度。
3. **把覆盖率显示出来。** 页面分别显示用户选中的路线数、已发现、待采样、两腿新鲜、过期、不可评估，以及最近完整扫描耗时。容量不足时列出实际覆盖和积压，轮转期间保留最后观察时间，过期机会立即退出可批准列表。
4. **滚动保存原始证据。** 按来源和大小轮转捕获段，校验归档可重放后回收已归档段。保留每个候选引用的两腿原始序号、版本和时间。归档失败时显示剩余容量和受影响来源。
5. **用负载结果确定容量。** 建议以 16、64、256 个选中品种分级测量覆盖一轮耗时、两腿时差 P95/P99、有效覆盖率、请求量、429 次数及每日存储增量。注入慢来源、断线重连、磁盘满和目录变更，核对无越界订阅、无过期推荐、重连后可重新预热。目标市场规模和延迟指标由测量后确定。

## 实施优先级与证据

先贯通前端配置、任意可选组合、核心资产投影与扫描覆盖。随后打通手动费率、稳定币平价和独立汇差，使每个候选都能解释净收益或拒绝原因。接着完成持久名单、空名单拒绝及限价单位修复，再从正式前端启动完整的双 IOC 周期，最后验证 Maker 撤换和同周期恢复。

上次审计运行的 160 项定向测试与前端类型检查通过。单独的 Web → Zig 批准探针使用当时已有二进制，首个请求返回 `InvalidPairAccount`；Python 夹具使用 production，Zig 账户夹具使用 simulation。修复验收应分别指定每腿的请求环境和真实账户环境，验证混合环境可配对且每腿准确路由。完整验收从空配置启动，同一笔人工批准贯穿下单、部分成交、恢复与最终对账，记录价格、数量和费用。现有结果仅覆盖上述离线验证。[批准探针](../../python/verify_scanner_console.py) · [核心夹具](../../src/testing/acceptance/core/scanner_authorization_acceptance.zig)
