# 跨所扫描滚动归档与容量验收

## 环境与口径

Windows 本机使用 Zig 0.17.0-dev.315+5b647b792 ReleaseFast 公共行情 worker。OKX production 现货与 Hyperliquid production 标准永续使用本地合成协议响应，双腿各占选中盘口数的一半。正式请求调度、Venue 限频、原生解码、DurableStore、候选发布和后台归档参与测量。429 退避另用注入响应验证。

运行 `python python/verify_scanner_capacity.py --seconds 420 --rounds 1`。每 500 ms 推进扫描与采样覆盖，统计从启动到第一轮完成或超时。全轮要求每条路线均取得本轮内、时差不超过 1 秒的双腿盘口。有效覆盖率等于每次采样时仍满足 5 秒 TTL、1 秒时差及健康条件的路线数除以发现路线数。计算双腿时差 P95/P99 时，两腿时间均较该路线的上一条统计样本更新才计入，包含超出 1 秒门槛的样本。请求统计包含盘口、目录、元数据和批量粗筛。存储增长采用状态目录逻辑字节差，包含热段和归档，日增量按从启扫到停扫并完成归档的时长线性外推。

## 存储和故障验收

- 认证机会页产生候选后从运行中停止，等两条原始捕获热段回收，复算材料仍能按两腿各自的 RawIngress 序号取回原文。原文 SHA-256、会话、品种、规则版本、单调接收时刻和 UTC 时刻可核对，复算快照一致。用 32 KiB 分段预算重复采样验证按大小轮转，双腿保持新鲜。
- 注入单个慢行情来源，其他路线继续完成采样，排除资产没有请求盘口。断连撤回受影响路线，恢复后重新预热。目录刷新覆盖新增、下架、规则变化及旧 worker 结果清除。超过 TTL 的路线退出可批准列表。
- 注入磁盘可用空间为零，认证 API 仅标记尝试新建段的来源，另一腿继续采样。恢复空间后重新预热。归档重命名返回 ENOSPC 时热段及回放保持可用；重试成功后热段路径释放。阻塞一路原生审计时行情采样与认证 API 仍能推进。
- 模拟一条已提交的捕获头缺少后续分块，原生校验确认完整前缀可归档并按原序号回放。损坏或无法验证的段保留待重试，页面显示相关来源。
- 另用公共 transport 限频测试注入 429，验证 Retry-After 按 Venue 执行，OKX 请求可继续推进。

16 盘口另以 60 秒窗口重复扫描，完成八轮。首轮 18.859 秒，后七轮 3.297–11.750 秒。有效覆盖均值 48.78%，峰值 100%，P95/P99 为 1.516/3.438 秒。共 217 次请求、0 次 429，字节增加 480,365 B，外推每日 0.630 GB。

每档最多 16 个活动盘口 worker。轮转时新 worker 必须重验元数据，Hyperliquid 元数据请求需要留出 1.2 秒的限频间隔，盘口和批量报价各留出 0.12 秒。64 和 256 盘口首轮分别发出 25 和 104 次 Hyperliquid 元数据请求。随着轮转增加，元数据重验和限频拉长整轮，积压期间不少盘口已过 5 秒时效。16 盘口可以反复完成采样且曾达到全路新鲜。三档负载都未达到持续全路新鲜。

归档保留在同一磁盘时，保留天数可按「磁盘可用字节减 4 MiB」除以该档每日增量估算。这个值随盘口大小、元数据刷新量、请求频率和共享磁盘占用改变。
