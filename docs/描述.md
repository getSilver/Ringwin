可以。真正要做的是一个 **Cross-Exchange Opportunity Scanner（跨所套利机会扫描器）**。它先不负责下单，而是持续回答三个问题：

> 哪些币长期存在跨所价差？
> 净价差有多大、能吃多少量？
> 一天真正出现多少次“独立可套利机会”？

其中第三个问题最容易统计错。**不能把每次 WebSocket 行情更新都算成一次套利机会**，而应该把连续存在的一段价差定义成一个 `Opportunity Event`。

### 1. 先找两个交易所的共同市场

例如 Binance 与 OKX，各自获取现货交易对列表，然后取交集：

```text
Binance                OKX
BTC/USDT      ───────  BTC/USDT
ETH/USDT      ───────  ETH/USDT
SOL/USDT      ───────  SOL/USDT
XRP/USDT      ───────  XRP/USDT
DOGE/USDT     ───────  DOGE/USDT
...
```

内部一定要做统一格式：

```text
BTCUSDT
BTC-USDT
BTC_USDT

↓

BTC/USDT
```

同时过滤：

```text
Trading status != active
杠杆代币
极低流动性币
稳定币/报价币异常市场
不支持充提的资产（视策略需要）
```

第一阶段建议只研究：

```text
XXX / USDT
```

不要一开始就混：

```text
USDC
BTC
ETH
FDUSD
```

否则还要把 quote currency basis 算进去。

## 2. 两个方向都必须扫描

假设两个交易所：

```text
A = Binance
B = OKX
```

同一个 BTC/USDT 实际有两个套利方向。

方向 1：

```text
A 买
B 卖

SpreadAB =
B.bid / A.ask - 1
```

方向 2：

```text
B 买
A 卖

SpreadBA =
A.bid / B.ask - 1
```

例如：

```text
Binance
Bid 100000
Ask 100010

OKX
Bid 100080
Ask 100090
```

那么：

```text
Binance BUY → OKX SELL

100080 / 100010 - 1
≈ 0.06999%
≈ 7 bp
```

但 **7 bp 并不是可套利利润**。

---

# 3. 真正应该扫描的是 Net Edge

例如两边 Taker Fee：

```text
Binance = 5 bp
OKX     = 5 bp
```

那么这个 7 bp 的机会：

```text
Gross Edge = +7 bp
Fee        = -10 bp

Net Edge   = -3 bp
```

实际上不能套利。

因此 Scanner 应计算：

```text
NetEdge =
ExecutableSpread
- BuyFee
- SellFee
- Slippage
- RebalanceCost
- RiskBuffer
```

比如设：

```text
Minimum Net Edge = 10 bp
```

那么：

```text
NetEdge >= 10 bp
```

才定义为：

```text
Arbitrageable
```

而不是只要：

```text
BidB > AskA
```

就算套利。

---

# 4. 更关键：必须按 OrderBook 深度扫描

假设：

```text
A Ask

100.00    10 USDT
100.10    20 USDT
101.00    50,000 USDT
```

B Bid：

```text
100.50    10 USDT
100.40    20 USDT
100.00    50,000 USDT
```

只看 Best Bid / Ask：

```text
100.50 / 100.00 - 1
= 0.5%
```

看起来是巨大机会。

但实际上只有：

```text
$10
```

可以套利。

这种机会没有意义。

所以你的 Scanner 应同时计算几个标准 Size，例如：

```text
$100
$500
$1,000
$5,000
$10,000
$50,000
```

分别计算两边 VWAP。

最终你会得到：

| Coin |  $500 |  $1K |   $5K | $10K |
| ---- | ----: | ---: | ----: | ---: |
| BTC  |  14bp | 13bp |  11bp |  8bp |
| ETH  |  18bp | 16bp |   9bp |  3bp |
| SOL  |  35bp | 28bp |  12bp | -4bp |
| ABC  | 180bp | 90bp | -20bp |    - |

这样信息价值远高于单纯看：

```text
最大价差是多少？
```

因为真正决定收益的是：

> **Spread × Executable Size**

# 5. “一天出现多少次套利机会”应该这样定义

这是整个统计系统最关键的一点。

比如 BTC 在 10 秒内行情：

```text
12:00:00.000   8 bp
12:00:00.100  11 bp  ← 可套利
12:00:00.200  13 bp
12:00:00.300  12 bp
12:00:00.400  15 bp
12:00:00.500  14 bp
12:00:01.000   9 bp  ← 消失
```

不能统计成：

```text
4~5 次套利机会
```

实际上应该是：

```text
1 次套利事件
```

也就是：

```text
Opportunity Start
        ↓
────────────────
连续满足条件
────────────────
        ↓
Opportunity End
```

建议建立状态机：

```text
CLOSED
  │
  │ NetEdge >= EntryThreshold
  ▼
OPEN
  │
  │ NetEdge < ExitThreshold
  ▼
CLOSED
```

例如：

```text
EntryThreshold = 12 bp
ExitThreshold  = 8 bp
```

这种 hysteresis 很重要。

否则行情：

```text
11.9
12.1
11.9
12.1
11.8
12.2
```

可能被系统错误统计成三次机会。

实际上它应该看成一个价差事件。

# 8. 我更建议设计一个 Opportunity Score

不要只按：

```text
套利次数
```

排名。

因为可能：

```text
币 A
100 次 × 1 秒 × 20bp × $10K

币 B
1000 次 × 50ms × 100bp × $50
```

币 A 对你的系统显然价值高得多。

可以定义一个研究指标：

```text
Opportunity Value
≈
Σ(
    NetEdge
    × ExecutableNotional
    × ExecutionProbability
)
```

例如：

```text
SOL

一天 50 个事件

平均：
Edge = 18bp
Executable = $5,000
Execution probability = 70%
```

理论 Opportunity Value：

```text
50 ×
5000 ×
0.0018 ×
0.7

≈ $315/day
```

注意这不是实际利润，只适合作为**币种排名指标**。

真实收益还会被：

```text
竞争
延迟
库存约束
双腿成交差
API 限频
资金利用率
```

进一步压缩。

对每个币统计：

```text

Net Edge >= 10bp
Net Edge >= 15bp
Net Edge >= 20bp
Net Edge >= 30bp
Net Edge >= 50bp
```

例如：

```text
SOL / Binance ↔ OKX

过去 24h：

>= 5 bp      418 events
>= 10 bp     172
>= 15 bp      83
>= 20 bp      41
>= 30 bp      12
>= 50 bp       2
```

同时再加：

```text
Duration > 100ms
Duration > 250ms
Duration > 500ms
Duration > 1s
Duration > 5s
```

最终可能发现：

```text
>=20bp
41次

但是：

>500ms
只有17次
```

那么真正值得你的系统参与的大约就是：

```text
17 个
```

而不是 41 个。

## 第一版 Scanner，我建议暂时完全不交易

架构做成：

```text
Binance WS ──────────┐
                     │
OKX WS ──────────────┤
                     ▼
              Local OrderBooks
                     │
                     ▼
              Symbol Matcher
                     │
                     ▼
         Cross Exchange Scanner
                     │
           ┌─────────┴──────────┐
           ▼                    ▼
      A → B Edge            B → A Edge
           │                    │
           └─────────┬──────────┘
                     ▼
            Opportunity FSM
                     │
                     ▼
              Event Database
                     │
                     ▼
                Analytics
                     │
          ┌──────────┼─────────┐
          ▼          ▼         ▼
        Count      Duration    EV
```

**先连续收集 7～30 天数据，再决定哪些币值得进入真实交易名单。**

这一步非常重要，因为你可能最后发现真正有意义的不是“价差最大的币”，而是：

> **价差适中 + 出现频率高 + 持续时间够长 + 盘口够深 + 双向机会相对均衡**

这种币最适合跨所套利。对于后面要做自动交易，我甚至会把币种选择公式直接定义为：

```text
Arbitrage Quality
=
Net Edge
× Depth
× Frequency
× Duration
× Fill Probability
÷ Inventory Cost
```

这比单独统计“今天出现了多少次价差”有用得多。
