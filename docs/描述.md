Me:帮我规划一份跨数字交易所价差套利的方案

可以。对于“跨数字资产交易所价差套利”，我建议不要做成传统的“发现 A 便宜 → 买入 → 提币到 B → 卖出”模式，而是设计成一套**预置库存、双腿并发成交、动态再平衡的市场中性系统**。这样才比较接近真正可以长期运行的交易基础设施。

### 一、总体策略架构

最适合作为第一阶段的是：

**Spot ↔ Spot 跨所套利**

例如同时接入 Exchange A 和 Exchange B：

* A：BTC/USDT Ask = 100,000
* B：BTC/USDT Bid = 100,300

系统提前在：

* A 存 USDT
* B 存 BTC

当扣除手续费、滑点以及安全余量以后仍然有利润时：

> A 买 BTC
> B 同时卖 BTC

而不是：

> A 买 BTC → 提 BTC → 等区块确认 → B 到账 → 再卖

后一种模式会把几秒钟的套利问题变成几分钟甚至几十分钟的方向性持仓问题。

## 三、价差不能直接用 Bid / Ask 算

最容易犯的错误就是：

```text
spread = B.bid - A.ask
```

真正应该计算的是**可执行价差**。

假设计划套利 $20,000 BTC，系统应该直接扫描 OrderBook depth，计算：

```text
BuyVWAP_A(20,000 USD)
SellVWAP_B(20,000 USD)
```

然后：

```text
GrossSpread
=
SellVWAP_B / BuyVWAP_A - 1
```

再扣除：

```text
Fee_A
Fee_B
Slippage
Expected adverse selection
Funding / borrow cost
Stablecoin basis
Rebalance cost
Safety margin
```

最终：

```text
NetEdge
=
GrossSpread
- FeeA
- FeeB
- SlippageA
- SlippageB
- RebalanceCost
- RiskBuffer
```

只有：

```text
NetEdge > MinimumRequiredEdge
```

才允许交易。

比如：

```text
原始价差       35 bp
A手续费        -5 bp
B手续费        -5 bp
预计滑点        -6 bp
库存成本        -2 bp
安全余量        -5 bp
---------------------
预期净利润      12 bp
```

这种机会才具有意义。

因此系统内部最好全部统一使用：

```text
1 bp = 0.01%
```

方便风控和统计。

# 四、最重要的设计：资金预置

例如你准备：

```text
Exchange A
BTC   0.5
USDT  50,000

Exchange B
BTC   0.5
USDT  50,000
```

总资产：

```text
BTC   1 BTC
USDT  100,000
```

假设出现：

```text
A BTC = 100,000
B BTC = 100,300
```

执行：

```text
A:
BUY 0.1 BTC
USDT -10,000
BTC  +0.1

B:
SELL 0.1 BTC
BTC  -0.1
USDT +10,030
```

你的**总 BTC 数量基本不变**：

```text
BTC:
A +0.1
B -0.1
-----------
Net = 0
```

只是资产在两个交易所之间发生了迁移。

这就是跨所套利非常核心的概念：

> 价格套利实际上会逐渐转换成**库存失衡问题**。

# 五、Inventory Manager 比套利算法本身更重要

假设一直都是：

```text
A 便宜
B 贵
```

系统不断：

```text
A BUY
B SELL
```

最终就会出现：

```text
A:
BTC  ██████████
USDT ░

B:
BTC  ░
USDT ██████████
```

这时候虽然还有套利机会，你已经无法继续交易。

因此每个交易所应该定义目标库存，例如：

```text
BTC target = 50%
USDT target = 50%
```

并定义：

```text
Soft Limit
Hard Limit
```

例如：

```text
BTC inventory deviation:

< 10%       NORMAL
10-25%      REDUCE SIZE
25-40%      REBALANCE
>40%        STOP ONE DIRECTION
```

具体比例以后根据资金规模和币种波动率优化。

# 六、库存再平衡建议做成三级机制

第一优先级应该是：

### Reverse Arbitrage

等待出现：

```text
B 便宜
A 贵
```

然后反向：

```text
B BUY
A SELL
```

这不仅赚钱，而且自动恢复库存。

这是最理想的情况。

第二种是使用其他市场进行内部再平衡，比如：

```text
BTC/USDT
BTC/USDC
USDC/USDT
```

或者利用永续合约暂时管理 Delta。

最后才是：

```text
Exchange A
      ↓
 blockchain
      ↓
Exchange B
```

也就是链上提币。

链上转账应该属于：

> Treasury / Inventory Management

而不是：

> Arbitrage Execution

这两个一定要在架构上分开。

# 七、双腿执行是整个系统最危险的地方

套利信号可能是：

```text
BUY  A  1 BTC
SELL B  1 BTC
```

但真实情况可能出现：

```text
A FILLED 1 BTC

B FILLED 0.3 BTC
```

这时候系统实际上变成：

```text
LONG 0.7 BTC
```

这叫 **Leg Risk**。

因此 Execution Engine 必须是状态机，而不能简单写：

```python
buy()
sell()
```

建议状态类似：

```text
NEW
 │
 ▼
SUBMITTING
 │
 ├── A ACK
 └── B ACK
 │
 ▼
PARTIAL
 │
 ├── MATCHED
 │
 └── IMBALANCED
       │
       ▼
     HEDGE
       │
       ▼
   COMPLETED
```

## 八、下单策略

第一版我反而建议：

**IOC + Taker**

而不是追求 Maker。

因为套利系统第一目标是：

> 保证双腿风险可控

而不是：

> 每一笔省几 bp 手续费。

例如：

```text
Buy A IOC
Sell B IOC
```

双腿并发发送，而不是：

```text
await buy_A()

await sell_B()
```

应该接近：

```text
submit(A)
submit(B)
```

同时发出。

然后根据成交结果计算：

```text
filled_A
filled_B
```

如果：

```text
abs(filled_A - filled_B) > tolerance
```

立即进入：

```text
Emergency Hedge
```

如果这是要接到你的交易系统里面，我会把核心抽象成：

```text

                      ▼

                      ▼
               ExecutionPlan
                 /        \

         Exchange A     Exchange B
              │              │
              └──────┬───────┘
                     ▼
                FillMatcher

            ▼                 ▼

            │
            ▼
     InventoryManager
            │
       ┌────┴─────┐
       ▼          ▼

```

其中最重要的设计思想是：

> **Strategy 只负责发现机会，Execution 负责成交，Risk 有权否决 Strategy，Ledger 才是真实资产状态。**

不要让策略模块自己直接调用交易所：

```text
❌ Strategy → Binance API
❌ Strategy → OKX API
```

而应该：

```text
Strategy
   ↓
ExecutionPlan
   ↓
RiskEngine
   ↓
ExecutionEngine
   ↓
Exchange Adapter
```

这样以后无论加入三角套利、Funding Arbitrage、做市还是期现套利，都可以复用同一套执行和风控基础设施。

最后需要特别强调一点：**跨所价差套利不是“无风险套利”**。它把方向风险大幅降低了，但仍然存在成交腿风险、交易所对手方风险、API/网络故障、稳定币基差、资金冻结、盘口瞬时消失以及库存失衡等风险。因此真正决定这套系统能否长期运行的，往往不是“发现价差”的算法，而是 **Execution + Inventory + Risk**。

Me: 要如何发现 2个交易所之间有哪些币有套利空间，机会，出现可套利的次数？

可以。真正要做的是一个 **Cross-Exchange Opportunity Scanner（跨所套利机会扫描器）**。它先不负责下单，而是持续回答三个问题：

> 哪些币长期存在跨所价差？
> 净价差有多大、能吃多少量？
> 一天真正出现多少次“独立可套利机会”？

其中第三个问题最容易统计错。**不能把每次 WebSocket 行情更新都算成一次套利机会**，而应该把连续存在的一段价差定义成一个 `Opportunity Event`。

### 1. 先找两个交易所的共同市场

例如 Binance 与 OKX，各自获取现货交易对列表，然后取交集：

```text
Binance                OKX
BTC/USDT      ───────  BTC/USDT
ETH/USDT      ───────  ETH/USDT
SOL/USDT      ───────  SOL/USDT
XRP/USDT      ───────  XRP/USDT
DOGE/USDT     ───────  DOGE/USDT
...
```

内部一定要做统一格式：

```text
BTCUSDT
BTC-USDT
BTC_USDT

↓

BTC/USDT
```

同时过滤：

```text
Trading status != active
杠杆代币
极低流动性币
稳定币/报价币异常市场
不支持充提的资产（视策略需要）
```

第一阶段建议只研究：

```text
XXX / USDT
```

不要一开始就混：

```text
USDC
BTC
ETH
FDUSD
```

否则还要把 quote currency basis 算进去。

## 2. 两个方向都必须扫描

假设两个交易所：

```text
A = Binance
B = OKX
```

同一个 BTC/USDT 实际有两个套利方向。

方向 1：

```text
A 买
B 卖

SpreadAB =
B.bid / A.ask - 1
```

方向 2：

```text
B 买
A 卖

SpreadBA =
A.bid / B.ask - 1
```

例如：

```text
Binance
Bid 100000
Ask 100010

OKX
Bid 100080
Ask 100090
```

那么：

```text
Binance BUY → OKX SELL

100080 / 100010 - 1
≈ 0.06999%
≈ 7 bp
```

但 **7 bp 并不是可套利利润**。

# 3. 真正应该扫描的是 Net Edge

例如两边 Taker Fee：

```text
Binance = 5 bp
OKX     = 5 bp
```

那么这个 7 bp 的机会：

```text
Gross Edge = +7 bp
Fee        = -10 bp

Net Edge   = -3 bp
```

实际上不能套利。

因此 Scanner 应计算：

```text
NetEdge =
ExecutableSpread
- BuyFee
- SellFee
- Slippage
- RebalanceCost
- RiskBuffer
```

比如设：

```text
Minimum Net Edge = 10 bp
```

那么：

```text
NetEdge >= 10 bp
```

才定义为：

```text
Arbitrageable
```

而不是只要：

```text
BidB > AskA
```

就算套利。

# 4. 更关键：必须按 OrderBook 深度扫描

假设：

```text
A Ask

100.00    10 USDT
100.10    20 USDT
101.00    50,000 USDT
```

B Bid：

```text
100.50    10 USDT
100.40    20 USDT
100.00    50,000 USDT
```

只看 Best Bid / Ask：

```text
100.50 / 100.00 - 1
= 0.5%
```

看起来是巨大机会。

但实际上只有：

```text
$10
```

可以套利。

这种机会没有意义。

所以你的 Scanner 应同时计算几个标准 Size，例如：

```text
$100
$500
$1,000
$5,000
$10,000
$50,000
```

分别计算两边 VWAP。

最终你会得到：

| Coin |  $500 |  $1K |   $5K | $10K |
| ---- | ----: | ---: | ----: | ---: |
| BTC  |  14bp | 13bp |  11bp |  8bp |
| ETH  |  18bp | 16bp |   9bp |  3bp |
| SOL  |  35bp | 28bp |  12bp | -4bp |
| ABC  | 180bp | 90bp | -20bp |    - |

这样信息价值远高于单纯看：

```text
最大价差是多少？
```

因为真正决定收益的是：

> **Spread × Executable Size**

# 5. “一天出现多少次套利机会”应该这样定义

这是整个统计系统最关键的一点。

比如 BTC 在 10 秒内行情：

```text
12:00:00.000   8 bp
12:00:00.100  11 bp  ← 可套利
12:00:00.200  13 bp
12:00:00.300  12 bp
12:00:00.400  15 bp
12:00:00.500  14 bp
12:00:01.000   9 bp  ← 消失
```

不能统计成：

```text
4~5 次套利机会
```

实际上应该是：

```text
1 次套利事件
```

也就是：

```text
Opportunity Start
        ↓
────────────────
连续满足条件
────────────────
        ↓
Opportunity End
```

建议建立状态机：

```text
CLOSED
  │
  │ NetEdge >= EntryThreshold
  ▼
OPEN
  │
  │ NetEdge < ExitThreshold
  ▼
CLOSED
```

例如：

```text
EntryThreshold = 12 bp
ExitThreshold  = 8 bp
```

这种 hysteresis 很重要。

否则行情：

```text
11.9
12.1
11.9
12.1
11.8
12.2
```

可能被系统错误统计成三次机会。

实际上它应该看成一个价差事件。

# 8. 我更建议设计一个 Opportunity Score

不要只按：

```text
套利次数
```

排名。

因为可能：

```text
币 A
100 次 × 1 秒 × 20bp × $10K

币 B
1000 次 × 50ms × 100bp × $50
```

币 A 对你的系统显然价值高得多。

可以定义一个研究指标：

```text
Opportunity Value
≈
Σ(
    NetEdge
    × ExecutableNotional
    × ExecutionProbability
)
```

例如：

```text
SOL

一天 50 个事件

平均：
Edge = 18bp
Executable = $5,000
Execution probability = 70%
```

理论 Opportunity Value：

```text
50 ×
5000 ×
0.0018 ×
0.7

≈ $315/day
```

注意这不是实际利润，只适合作为**币种排名指标**。

真实收益还会被：

```text
竞争
延迟
库存约束
双腿成交差
API 限频
资金利用率
```

进一步压缩。

```text
Net Edge >= 10bp
Net Edge >= 15bp
Net Edge >= 20bp

Net Edge >= 50bp
```

```text
>= 5 bp      418 events

```

同时再加：

```text

Duration > 250ms

Duration > 1s
Duration > 5s
```

最终可能发现：

```text
>=20bp
41次

但是：

>500ms
只有17次
```

那么真正值得你的系统参与的大约就是：

```text
17 个
```

而不是 41 个。

```text
          ▼          ▼         ▼
        Count      Duration    EV
```

**先连续收集 7～30 天数据，再决定哪些币值得进入真实交易名单。**

这一步非常重要，因为你可能最后发现真正有意义的不是“价差最大的币”，而是：

> **价差适中 + 出现频率高 + 持续时间够长 + 盘口够深 + 双向机会相对均衡**

这种币最适合跨所套利。对于后面要做自动交易，我甚至会把币种选择公式直接定义为：

```text
Arbitrage Quality
=
Net Edge
× Depth
× Frequency
× Duration
× Fill Probability
÷ Inventory Cost
```

这比单独统计“今天出现了多少次价差”有用得多。
