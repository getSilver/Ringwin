# 在同一决策域内拥有跨账户组与周期占用

当前 TradingShard 绑定单账户；多账户 Gateway 路由、内部 IntentGroup 与同账户多 shard 协调不能组合成跨账户共同提交。H2 的共同准入与 H3 的周期恢复需要同一份权威事实。

提议将首版限定为同一 DecisionDomain 的一个 TradingShard 和一个 decision Writer，按账户分区拥有余额、订单经济归属与风险占用，并在一次持久事务内提交完整组、资金预留和账户品种周期占用。所有争用相同账户品种的新增周期入口必须共置或拒绝；其他品种共享账户资金仍受每账户保守 RiskLease 约束。Python 只保留策略私有状态和核心引用。该方向尚待用户确认，未实施、未授予新发送能力。

## Considered Options

- 单 owner 的有界多账户状态：避免跨 shard 提交协议，代价是扩展核心账户表示、所有命名空间及持久恢复格式，并限制竞争集合的放置。
- 保留单账户 shard 并增加跨账户协调者：需要独立权威、prepare/commit/ack、冻结与恢复协议；不能将 ADR0016 的单账户协调 Writer 借作其他账户的提交身份。
- 独立接受两腿或 Python 锁表：不能满足共同准入与唯一权威要求。

## Consequences

若接受该方案，跨 shard 组首版拒绝，现有经济状态不自动迁移；核心与 Gateway 等实际受影响的格式分别升级并失败关闭旧的不兼容格式。共同提交仅保证内部准入与占用原子性，不保证外部发送或成交原子性。Unknown、未闭合经济事实和未确认残余政策保持占用；恢复不能重发、延长期限或重新授权。先历史发布、再持久提交、后回收仍遵守 ADR0011/0013/0014/0016。

完整备选、竞争与故障向量、容量及兼容合同、建议拆分见 [H2/H3 权威边界设计提案](../../.scratch/cross-venue-core-interface/authority-design.md)。确认架构与拆分前本 ADR 保持 proposed。
