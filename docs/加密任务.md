对 RingWin，建议首版采用：

> 本地加密 `CredentialStore` + SystemOwner 启动时手工解锁 + 交易所权限/IP 白名单 + 仅 Execution Gateway 进程持有明文。

先不要急着引入 Vault 集群、HSM 或自建通用密钥平台。等进入多节点、HA 或云部署时，再把存储后端替换成 Vault/云 Secret Manager。

zig标准库 std.crypto.secureZero ，std.process.lockMemory 、 protectMemory 最好自己封装一层类型做一个结构体（如 Secret），内部管理内存锁定、受控访问（expose）和自动清零，对外提供统一安全接口。

- `TradingCredential` 必须绑定 Venue、账户、环境和用途，且生产交易凭证不得提现。[GLOSSARY.md](/D:/github/Ringwin/GLOSSARY.md:813)

- 首版 `CredentialStore` 采用加密静态存储，由 SystemOwner 启动时手工解锁。[GLOSSARY.md](/D:/github/Ringwin/GLOSSARY.md:821)
- 观察凭证和执行凭证必须分离。[GLOSSARY.md](/D:/github/Ringwin/GLOSSARY.md:825)

但目前 Demo 脚本仍从 `.env.local` 读取密钥并临时写入进程环境变量，例如 [run-okx-demo-live-acceptance.ps1](/D:/github/Ringwin/tools/run-okx-demo-live-acceptance.ps1:37)。这只能算开发方案，不是生产托管。

## 推荐架构

```text
SystemOwner
    │ 启动时通过 TTY 输入解锁口令
    ▼
Encrypted CredentialStore
    │ 解密并校验绑定关系
    ▼
Locked SecretMaterial
    │ 只交给当前 Adapter session
    ▼
Execution Gateway / VenueAdapter
    │ 在进程内签名请求
    ▼
Exchange private endpoint
```

核心约束：

1. 每个 `Venue + Environment + ExchangeAccount + Purpose` 使用独立 API key。
2. ObservationCredential 只有 Read 权限。
3. ExecutionCredential 只有 Read + Trade，禁止 Withdraw、Transfer、账户管理。
4. 生产与 Demo/Testnet 完全分库、分密钥、分解锁口令。
5. 策略进程、Python Host、研究工具、CanonicalEvent、journal 和 snapshot 永远拿不到密钥。
6. VenueAdapter 只取得短生命周期的内存句柄，不能把凭证复制到普通字符串。

OKX 官方将权限区分为 Read、Trade、Withdraw，并建议绑定 IP；因此生产执行 key 应只开 Read/Trade、关闭 Withdraw，并绑定执行节点出口 IP。[OKX API documentation](https://app.okx.com/docs-v5/en/)

## 加密存储格式

不要自己设计密码算法，但可以定义一个很小的稳定容器：

```text
CredentialEnvelope
  format_version
  credential_id
  venue
  environment
  exchange_account
  purpose
  credential_version
  state
  kdf_algorithm + parameters
  salt
  nonce
  ciphertext
  authentication_tag
```

推荐：

- 解锁口令通过 Argon2id 派生 KEK；
- 每份凭证使用随机 DEK；
- 使用 XChaCha20-Poly1305 AEAD 加密；
- Venue、账户、环境、用途、版本作为 authenticated associated data；
- 解密失败、绑定不符、文件损坏或版本未知全部 fail-closed。

libsodium 将 Argon2id 作为默认 password-hashing/KDF 算法，并推荐在不要求互操作时使用 XChaCha20-Poly1305；AEAD 同时提供保密性和篡改检测。[libsodium password hashing](https://doc.libsodium.org/password_hashing/default_phf)、[XChaCha20-Poly1305](https://doc.libsodium.org/secret-key_cryptography/aead/chacha20-poly1305)

## 运行时处理

明文密钥只在 Execution Gateway/VenueAdapter 进程中存在：

- 使用固定大小 `[]u8`，避免普通字符串及隐式复制；
- 解锁后调用 `mlock`/`VirtualLock`；生产环境锁定失败就不开放新增风险；
- 使用完立即显式清零；
- 禁止格式化、Debug 输出、panic payload 和错误链携带 SecretMaterial；
- Gateway 进程禁用或严格控制 core dump；
- 不通过命令行参数、环境变量、IPC、共享内存或 journal 传递；
- 日志只能记录 `credential_id/version/state`，不能记录 API key、secret、passphrase 或签名输入。

OWASP 同样建议最小权限、集中审计、轮换、缩短明文驻留时间，并指出环境变量可能被其他进程、日志或 dump 暴露。[OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

## 轮换流程

不要覆盖旧密钥，应使用现有的 `Staged → Active → Retiring → Revoked` 状态机：

1. 在交易所创建新 key，关闭 Withdraw/Transfer，并绑定固定 IP。
2. 以 `Staged` 写入 CredentialStore。
3. 用独立 ObservationCredential 完成账户、持仓、订单和权限预检。
4. 创建新的 AdapterSession，不在旧 session 中原地换密钥。
5. 暂停新增风险，排空或对账旧 session 的未完成订单。
6. 原子激活新 credential/version/session。
7. 将旧 key 标记 `Retiring`，确认无 Unknown 后在交易所撤销。
8. 本地标记 `Revoked`；配置回滚也不得重新激活它。

NIST 的密钥管理指导要求明确管理密钥生命周期、使用期限、保护、备份及泄露后的恢复流程。[NIST SP 800-57 Part 1 Rev. 5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final)

## 泄露处置

检测到疑似泄露时顺序必须固定：

1. 立即关闭对应账户的新增风险 SafetyGate。
2. 撤销交易所旧 key，并隔离节点/IP。
3. 使用 ObservationCredential 完整对账订单、成交、仓位和余额。
4. 创建全新 ExecutionCredential，不复用旧 secret。
5. 如果 CredentialStore 或解锁口令可能泄露，同时轮换 KEK/解锁口令并重新加密全部凭证。
6. 由 SystemOwner 审阅事件记录后重新授权交易。

## 什么时候引入 Vault

出现以下任一条件再引入 Vault 或云 Secret Manager：

- 多生产节点；
- HA/自动切换；
- 多个运维人员；
- 需要集中审计或自动轮换；
- 不希望节点长期保存加密凭证文件。

届时应用通过 MachineIdentity/Workload Identity 向 Vault 取指定 credential，避免给应用再配置一个长期 Vault token。Vault Agent 支持自动认证、续租和向受限文件注入静态 secret。[HashiCorp Vault Agent](https://developer.hashicorp.com/vault/docs/agent-and-proxy/agent)

对当前 RingWin，合理的开发顺序是：先完成加密文件型 `CredentialStore`、内存保护、权限预检、轮换状态机和泄露测试；Vault、TPM 自动解封及 HSM 签名留到 HA/部署阶段。
